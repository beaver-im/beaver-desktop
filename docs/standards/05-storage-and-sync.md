# 第6章　数据库、结构升级、消息与同步一致性

## 6.1 分开“定义、读写、业务、同步”

**事实**：本地库使用 SQLite / Drizzle，入口 [db.ts](../../src/main/database/db.ts)；
[init/index.ts](../../src/main/database/init/index.ts) 组织域建表并调用包注册初始化；
消息实例可沿 [table](../../src/main/database/tables/chat/message.ts)、[service](../../src/main/database/services/chat/message.ts)、
[business](../../src/main/business/chat/message.ts) 追踪。

**新代码约束**：表结构放 tables，持久读写放 services，发送/补齐等业务编排放 business，远端版本补齐放 datasync。
禁止 renderer/Pinia/普通 IPC 分发器里直接复制 SQL；同一业务状态更新只保留明确的写入口。
多表同一不变量的修改需要事务/等效一致性策略；事务边界随业务定义，不为了“统一”包住网络等待。

## 6.2 改表不能只改类型

新增字段/索引时按顺序核对：

1. 表定义和实际初始化 SQL/逻辑；Drizzle 类型变化不自动同步已有库文件。
2. 不需要为了兼容旧版数据格式编写多层历史兼容/双写代码；需要调整或删除列/表时，直接改齐表定义、初始化、service、business 与同步读写，删除不需要的旧字段/旧表。
3. service 默认值、空值、唯一约束和索引；business 与同步序列化/反序列化。
4. 用隔离临时数据库验证初始化、读写与异常恢复；本机或自部署环境仍可能存有用户真实本地库，未经明确授权不得直接删除或清空已有库文件。没有证据时不宣称仓里有成熟统一迁移框架。

**正例（步骤示意）**：加一个字段时，同时更新表/初始化、service、同步映射，并验证旧结构打开后读写。
**反例**：只改 IXXX 类型编译成功就交付；或者打开真实聊天数据库执行 DROP TABLE 方便本地测试。

## 6.3 消息可靠性要沿完整状态链看

证据：[MessageManager](../../src/main/message-manager/index.ts)、[WsManager](../../src/main/ws-manager/index.ts)、
[DataSyncManager](../../src/main/datasync/manager.ts)。

| 变更 | 新代码需保持 / 检查 | 不能做 |
| --- | --- | --- |
| 发送/ACK | 本地待发、成功/失败/超时状态、重复 ACK 处理 | 一收到任意回执就把所有消息标成功 |
| 接收/落库 | 按实际消息标识/版本幂等，通知与写入顺序一致 | 只靠 UI 去重掩盖重复数据库记录 |
| 重连/补齐 | 版本/游标推进和落库一致，失败可重试 | 数据没写成功先推进游标导致永久漏消息 |
| 同步中来消息 | 保留普通消息排队与流式帧例外语义 | 把所有增量流都当持久消息或一律阻塞 |
| 换号/退出 | 库、连接、订阅、缓存切到正确用户 | 以窗口换页代替旧用户资源释放 |

这些是评审目标，不宣称本轮证明所有历史分支幂等或无竞态；真实字段/去重键以当域源码为准。
个人 Agent 与机器人连接模型按当前用户/机器人协议分别核实，协议变更需一起核对服务端。

## 6.4 验证清单

正常发送/超时/失败/重复回执、断线恢复、乱序重放、同步期间新消息、流式结束、换号不串数据。
记录哪些是自动测试、哪些手工验证、哪些没环境；命令见[第19章](../workflow.md)。
