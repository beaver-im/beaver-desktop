# 第10章　新增一个跨进程调用（IPC）

假设需求：“让界面读取允许范围内的文件元信息”。这是协议设计示例，不是仓库已有或本轮新增方法。

## 10.1 先画一条完整链

```text
页面动作 → 明确命名的 preload 方法 → 固定 command
       → main 来源/参数/权限检查 → 文件业务服务 → 可序列化结果
```

先查 [preload/electron/fs.ts](../../src/preload/electron/fs.ts) 与对应主进程 handler 能否满足，不重复开通道。
如果处理的是能力包独有功能，在本域包里实现并按[插件协议](../standards/06-plugin-lifecycle.md)接入，不挤进宿主万能 handler。

## 10.2 按顺序修改，避免“漏半条链”

1. **契约**：在 [common/type/ipc](../../src/common/type/ipc) / [type/preload](../../src/common/type/preload) 的所属领域定义参数与结果，明确错误语义。
2. **命令**：复用当前分发方式，在已有 command/事件定义处添加明确命令，不接收界面自选任意通道。
3. **main handler**：在 [render-to-main](../../src/main/ipc/render-to-main) 对应域接入。确认调用方窗口/会话，校验 unknown 输入、路径归属和资源访问范围。
4. **业务实现**：实际文件逻辑放已有系统/文件服务，handler 保持协议适配；限制路径和返回数据，不信任用户传来的绝对路径。
5. **preload**：在所属模块定义窄方法，通过 invoke 调用；更新聚合与类型。不要新增原始 ipcRenderer 的暴露。
6. **renderer**：只调用明确动作，处理失败/取消，防止关窗或换会话后更新过期状态。
7. **通知**：如果还要监听变化，一起设计订阅/精确退订及窗口生命周期，不做永久订阅。

第5章的[安全规则](../standards/04-electron-and-ipc.md)是协议评审门槛。示意名字不能不经核实复制成真实 API。

## 10.3 必须留出的验证用例

| 用例 | 预期 |
| --- | --- |
| 允许资源/合法参数 | 只返回约定字段 |
| 空、类型错误、未知字段/命令 | 可预测拒绝，不崩溃或执行默认高权限动作 |
| 未授权来源/未登录（如该能力需登录） | 在可信侧拒绝，不能只隐藏 UI |
| 越界路径/符号链接绕过 | 不访问授权根之外的资源 |
| 文件消失、执行超时、窗口关闭 | 有明确失败/取消行为，资源释放 |

使用隔离样例目录，不拿真实隐私文件做测试；main/renderer/平台类型的实际检查见[第19章](../workflow.md)。
**反例**：为了省两行类型直接传 data:any；主进程用 data.command 执行 shell；成功一次就省略权限/失败测试。
